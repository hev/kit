## In this release so far

Merged since v0.6.2. Upgrade with
`brew update && brew upgrade hev/tap/hev`.

- **`hev update`, channels and edge builds.** A host moves itself to the
  newest build on its channel with `hev update`: `release` (the default) or
  `edge`, the tip of the open release train, published as a pre-release on
  every push to the train branch once its tests pass. `--to VERSION` names a
  build, `--check` reports only and `--rollback` returns to the build it
  replaced. The archive's sha256 is checked against the build's manifest
  before anything is replaced; the new build is installed beside the old one
  and switched in atomically, runs in progress finish on the binary they
  started with, and hevd restarts onto it (a failed restart switches back).
  Homebrew installs are left to Homebrew. With `[update] auto = true` the
  daemon does it on a schedule; it is off by default.
  `hev dispatch hosts update --all` asks every host you own to update itself
  and reports each one's version before and after, and `hev dispatch hosts`
  shows each host's channel and whether it is behind. Only a host's owner can
  ask; the request names a channel and a version, never a binary or a URL.
  Hosts on 0.6.2 move by hand once.
  See [Updating and channels](https://hevkit.com/docs/updating).
- **Composable context, with narrowing.** An order can name a context recipe
  with `context:`: a JSON file in the repository listing the instruction and
  skill files the worker gets, in order, whole or cut to some sections with
  `keep` and `drop` by heading. Dispatch builds it into a bundle at launch,
  gives the worker its `context.md`, sets the worktree's instruction files to
  match while the worker runs (nothing is committed), and records the
  bundle's digest on the run and its sessions. For one dispatch,
  `hev context plan ORDER.md` lists the repository's instruction files and
  sections, `hev dispatch ORDER.md --context-file RECIPE` sends a narrowed
  recipe with the order, and the `hev-context` skill walks an agent and you
  through that review. `hev dispatch show` names the digest and
  `hev traces ls --context DIGEST` finds the sessions given it; the Asks tab
  shows it on each run attempt. Intake templates can use `context:` too. Every host
  that runs such an order needs 0.7.
  See [Composable context](https://hevkit.com/docs/context).
  ([#209](https://github.com/hev/kit/pull/209),
  [#213](https://github.com/hev/kit/pull/213))
- **Ask-rooted traces.** Dispatched work is grouped by the ask that started
  it: the ask is the root of a trace, and the orders, attempts, reworks,
  validation runs and worker sessions it caused hang under it. `hev dispatch`
  starts a trace, `--trace ID` (or `trace:` in the order) continues one, and
  `rework`, `retry`, `say`, `amend` and `validate` add a follow-up ask to the
  run's trace. Workers get `TRACEPARENT`, `HEV_TRACE_ID` and `HEV_SPAN_ID`, so
  what they dispatch joins the same trace. The dashboard's new **Asks** tab
  lists traces and opens each as one waterfall, down to the worker's turns.
  The list filters by user, host (asking or execution) and project, in a
  linkable URL, and shows asking host → execution hosts. Runs recorded before
  tracing are labelled as such and hidden by default; runs left untraced on
  purpose are listed as untraced, with the reason. With a hev layer
  key, hosts publish their runs' trace facts so one dashboard shows runs from
  every host; without one it shows this host's runs.
  See [Traces](https://hevkit.com/docs/traces#ask-rooted-traces).
  ([#208](https://github.com/hev/kit/pull/208))
- **Swarms.** One Markdown file puts an orchestrator and several workers on
  one problem: roles that split the work into pieces, race variants against
  each other, or run once after the others finish. `hev swarm up -f FILE`
  compiles it into an ordinary orchestrator and dispatch runs, and a reconcile
  tick launches the units, repairs a failed or stalled one in place on its own
  branch, settles races, and starts integration when the pieces are done. One
  role opens the swarm's one draft PR, and a person merges. `hev swarm ps`,
  `logs`, `say`, `pause`, `resume` and `down` manage it. This is phase 1:
  every unit runs on the host where you run `up`. Units the tick launches are
  recorded as untraced, with the reason.
  See [Swarms](https://hevkit.com/docs/swarms) and
  [Orchestrator examples](https://hevkit.com/docs/orchestrator-examples).
  ([#205](https://github.com/hev/kit/pull/205),
  [#207](https://github.com/hev/kit/pull/207))
- **The board needs no setup.** `hev board serve` with no hev layer key keeps
  the board in files under `~/.hev/board/` (`board.dir` or `HEV_BOARD_DIR`
  moves it) and needs no namespace or endpoint. Search matches words, and
  every command, filter and route works as before. With a key the board uses
  hev layer as it always has. `hev board whoami` and the server's startup line
  say which. An existing hev layer board must keep its key in the server's
  environment: without one it now starts on an empty board in files.
  See [Board](https://hevkit.com/docs/board#run-a-board-server).
  ([#189](https://github.com/hev/kit/pull/189))
- **Traces with no setup.** With no hev layer key, hevd captures and indexes
  sessions into files on the machine, under `~/.hev/archive/hev-traces/`
  (`[archive] dir` or `HEV_ARCHIVE_DIR` moves it), with no endpoint and no
  Docker. Secrets are scrubbed before the write, as before. A key saved in the
  config counts as a key, and one that is configured but cannot be read is an
  error rather than a quiet switch to files. Files are used only when nothing
  on the machine says hev layer (see the upgrade note below). `hev traces list`, `show` and
  `search`, `hev browse`, `hev outcomes` and `hev index` all work on the files;
  search there matches words, keeps every filter, and says so. `hev serve`
  shows the same sessions, transcripts, stats and search in the dashboard;
  grades and search by meaning need a hev layer key, and the page says so.
  See [Traces](https://hevkit.com/docs/traces#where-traces-are-kept).
  ([#190](https://github.com/hev/kit/pull/190),
  [#191](https://github.com/hev/kit/pull/191),
  [#192](https://github.com/hev/kit/pull/192))
- **Upgrading a machine that keeps traces in hev layer.** kit uses files only
  when nothing on the machine says hev layer. A `[layer]` endpoint or
  namespace in `~/.hev/config.toml`, `HEVLAYER_ENDPOINT`, a key reference
  (`HEVLAYER_API_KEY_OP_REF`) that cannot be read, or a capture daemon here
  that writes to hev layer each say it. On such a machine a `hev` command that
  finds no key stops with an error that names what it found and what to set,
  instead of reading or writing an empty archive under `~/.hev/archive`; no
  read creates that directory. Check each upgraded machine with `hev s`: it
  shows the running daemon's storage and this shell's separately, and flags
  them when they differ. The usual cause is a key given only to hevd's service
  unit: shells and dispatched workers never see it. Give them a way to read
  it: `api_key` under `[layer]`, or `HEVLAYER_API_KEY` or
  `HEVLAYER_API_KEY_OP_REF` in the environment of the shell that dispatches
  (workers now inherit the key reference variables, and read the key with the
  host's own 1Password token file). A worker with none of these fails with
  that error rather than searching an empty archive. To keep traces in files
  instead, remove `endpoint` and `namespace` from `[layer]`; name a file
  archive with `namespace` under `[archive]`. `hev daemon install` no longer
  writes a `[layer]` table, and `hev up` moves the retired local lane's
  namespace to `[archive]`.
  See [Traces](https://hevkit.com/docs/traces#where-traces-are-kept).
- **`hev up` needs no Docker.** With no key, `hev up` writes the config,
  installs hevd and the skills, and starts nothing in a container; run
  `hev serve` for the dashboard. `hev daemon status` says where traces go.
  With a hev layer key, and on the bring-your-own turbopuffer lane, `hev up`
  works as before. See [Install](https://hevkit.com/docs/install#start-the-daemon).
  ([#193](https://github.com/hev/kit/pull/193))
- **Images on the board.** `hev board post` and `reply` take `--image FILE`,
  up to 8 per message (PNG, JPEG, GIF or WebP, 10 MB each by default).
  `hev board read` lists them and `read --images DIR` saves them; the web UI
  shows them inline. The bytes stay on the board server's disk and the same
  image is stored once; with a hev layer key, only each image's name, type,
  size, dimensions and hash go to hev layer.
  See [Board](https://hevkit.com/docs/board#images).
  ([#194](https://github.com/hev/kit/pull/194))
- **Images in traces.** When a session shows its agent an image, such as a
  pasted screenshot or a browser capture, hevd keeps it, for Claude Code,
  Codex, pi and OpenCode. `hev traces show` marks where each image was,
  `hev traces images ID --out DIR` saves them, and the dashboard shows them
  inline. The bytes stay on the machine that captured them and each image is
  stored once; with a hev layer key, only its type, size, dimensions and hash
  go to hev layer. Text scrubbing can't see into pixels, so
  `[capture] images = false` or `HEVD_CAPTURE_IMAGES=0` turns image capture
  off. See [Traces](https://hevkit.com/docs/traces#images).
  ([#195](https://github.com/hev/kit/pull/195))
- **Every host reads 1Password through one cache.** hevd's memory-only
  secrets cache now switches on with no configuration when the
  service-account token is in `~/.config/op/token`. Scripts read through it
  with `x=$(hev secrets read REF)` or `eval "$(hev secrets env --ref A=REF)"`,
  and kit's own hev layer key and native gate go through it too, so a host
  spends one request per value per TTL. Every real request is logged, without
  values, to `~/.hev/secrets/op-reads.log`. A rate limit is answered once and
  then held host-wide until its reset, across restarts, and hevd stays up
  through it. `hev secrets status` shows hits, requests, the cooldown and the
  account's quota, and `hev secrets ping` checks the cache without a request.
  `hev update` restarts a host's secrets-only cache with hevd.
  See [Secrets](https://hevkit.com/docs/secrets).
  ([#203](https://github.com/hev/kit/pull/203))
- **Azure Key Vault beside 1Password.** `hev secrets read`, `env` and `run`
  take `azkv://VAULT/SECRET[/VERSION]` references as well as `op://`, mixed in
  one call, with the same cache, read log and one-attempt rule. Sign-in is
  never interactive: managed identity (Azure VM, Arc, App Service), workload
  identity, a service principal with a certificate or a client secret (which
  can itself be an `op://` reference), or an existing `az login`. The identity
  needs only the Key Vault Secrets User role. A 429 costs one request and
  `Retry-After` is honoured across processes, and a throttled vault never
  blocks 1Password. A Windows host can use Key Vault alone, with no `op`. The
  hev layer key takes either scheme in `HEVLAYER_API_KEY_REF`
  (`HEVLAYER_API_KEY_OP_REF` still works).
  See [Secrets](https://hevkit.com/docs/secrets#choose-a-provider).
  ([#206](https://github.com/hev/kit/pull/206))
- **Short invite codes for shared hosts.** `hev nodes invite alex` prints a
  code like `7K-Q4M2-XPWD`; the member runs
  `hev nodes join bot@HOST 7K-Q4M2-XPWD`, and the owner approves by name with
  `hev nodes pending` and `hev nodes accept alex`. The code is single use,
  expires, and locks after five wrong tries. The exchange runs over the host's
  existing sshd, opens no port, and a host that does not know the code cannot
  pass itself off as the owner's. `invite` also takes `--allow repos` and
  `--administrators`, and `hev nodes remove NAME` withdraws an open
  invitation. Invitations sent with the long codes keep working, and
  `hev nodes invite --long` still makes one.
  ([#183](https://github.com/hev/kit/pull/183))
- **Runs end done, blocked or needs-decision.** A dispatched worker finishes
  by naming its outcome. `hev dispatch ls` shows blocked runs and open
  decisions by default, with a new `DECISION` column, and notifications lead
  with the outcome. Answer a decision with
  `hev dispatch say NAME --resolve KEY "answer"`: the run is reworked on the
  same worktree, branch and PR, and every later prompt repeats the answer.
  A run with an open decision is not sent to browser validation.
  ([#184](https://github.com/hev/kit/pull/184))
- **`hev peers` matches the Python peers.** The `peers` commands, flags,
  output and state files are now built into `hev`, byte for byte compatible
  with the Python `peers`, so the two run side by side on one host and across
  hosts. A `peers` symlink to `hev` behaves like the Python executable.
  ([#180](https://github.com/hev/kit/pull/180))

### Fixed

- **`hev s` on macOS sees the running daemon.** Since 0.6.1, `hev s` printed
  `Daemon: stopped` on every Mac while hevd ran under launchd, and
  `hev daemon stop` could not find it. hev now asks launchd for this user's
  hevd. ([#171](https://github.com/hev/kit/pull/171))

### Removed

- **The local Postgres archive.** `hev up` with no key no longer runs a local
  hev layer in Docker (Postgres with pgvector, a CPU embedding model and the
  dashboard container at port 8099); `--store pgvector` and the store choice
  in `hev init` are gone. A machine set up that way keeps working after the
  upgrade: run `hev up` once and capture moves to files. Its old archive is
  not copied. hevd indexes the transcripts still on disk into the files, and
  `hev backfill` sends them to hev layer once you add a key. Sessions whose
  transcripts are gone, and grades saved with `hev eval put`, stay only in the
  old Docker volume. kit never stops or deletes the old containers or their
  volume: hevd, `hev up` and `hev down` print the commands to stop them and
  remove the volume when you are done with it. ([#193](https://github.com/hev/kit/pull/193))
- **`hev get`, `apply`, `describe`, `logs`, `wait`, `api-resources`,
  `controller`, `orders` and `runs`.** These forwarded to a coordination
  backend that is gone. Each now exits 1 with a message pointing at
  `hev dispatch` and `hev orchestrate`; nothing is run from `PATH`, and
  `HEV_RESOURCE_BACKEND` and `HEV_COORDINATION_BACKEND` are no longer read.
  Bare `hev` reports peers only.
  ([#174](https://github.com/hev/kit/pull/174))
