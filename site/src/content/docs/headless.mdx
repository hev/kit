A laptop can run a couple of workers, and they stop when the lid closes. A
headless machine runs many workers at once and keeps going overnight. Add one
and the laptop becomes the place you write orders, not the place they run.

A headless host is any machine the sending side can reach over SSH: a box in
the closet, a spare Mac, or a cloud VM. Setup is the same for each.

## Set it up like a new hire

Kit doesn't sandbox workers. The machine is the sandbox, so treat it the way
you'd treat a new employee's laptop:

- **Its own hardware.** Nothing on it you'd mind an agent reading.
- **Its own identity.** A bot account on your Git host (for example a
  `yourbot` GitHub user) with write access to the repos it works on, and
  nothing else. Its commits and PRs show up under that name.
- **Its own keys.** Model and service credentials issued to the bot, scoped
  and revocable, not copied from your laptop.
- **Its own repo list.** [Admission](/docs/admission) refuses orders for any
  repository the host doesn't list, whoever sends them.

If it goes wrong, revoke the bot's tokens and wipe the machine. Your laptop and
your own accounts were never in reach.

## What the target needs

- **`hev`**, the same version as the sender. See [install](/docs/install).
- **The harness**, `codex` or `claude`, installed and logged in as the user
  SSH connects as. Workers run without approvals or a sandbox, so give them a
  machine and an account you are willing to hand over.
- **Git, and tmux on Linux or macOS.** Windows targets use a detached process
  instead of tmux; see [Windows](/docs/windows).
- **A workspace with clones.** Each repository an order names must already be
  cloned under the workspace (`~/workspace` by default) with an `origin`
  remote. Dispatch fetches and creates worktrees; it never clones.
- **SSH reachable from the sender**, with key authentication and a known host
  key. Dispatch uses batch mode and strict host-key checking, so connect once
  by hand first.
- **Credentials for pushing**, if orders push branches and open pull requests:
  a Git credential and `gh` logged in, or `GH_TOKEN` in the SSH environment.

Run the daemon on the target too if you want its runs in your traces. On Linux,
`hev up` installs a systemd user service. Enable lingering to keep it running
after logout. Without a user manager, run `hev d` under your own supervisor.

## On a box on your network

Give the box a name in `~/.ssh/config` on your laptop:

```text
Host buildbox
  HostName buildbox.example.test
  User dev
```

Check that a non-interactive session finds everything:

```sh
ssh -o BatchMode=yes buildbox 'hev --help >/dev/null && git --version && tmux -V && codex --version'
```

## In the cloud

Start a VM, install the tools above, and log the harness in once over an
interactive SSH session. Then add the same kind of `~/.ssh/config` entry.
Nothing in hev kit is specific to a cloud provider. The VM needs no open
ports beyond SSH.

## Add the host on the sending side

In `~/.config/hev/dispatch.toml` on your laptop:

```toml
default_host = "buildbox"

[hosts.laptop]
local = true
cap = 2

[hosts.buildbox]
ssh = "buildbox"
cap = 8
path_prefix = ["~/.local/bin", "~/go/bin"]
```

| Key | Meaning |
| --- | --- |
| `ssh` | The SSH destination: an alias from `~/.ssh/config` or `user@host` |
| `cap` | Most runs the host takes at once. Required, at least 1 |
| `path_prefix` | Directories added to the remote `PATH`, for tools a non-login shell misses |
| `workspace` | Overrides the target's workspace for this host |
| `namespace` | Passed to workers as `HEVLAYER_NAMESPACE` |
| `os` | Set `"windows"` for a Windows target |

Then check it:

```sh
hev dispatch hosts
```

`hosts` shows each host's cap, running and free slots, whether it is reachable,
and its `hev` version. A version that differs from yours is flagged.

Send an order with `host: buildbox`, or override any order with
`--host buildbox`. `hev dispatch run` with no host picks `default_host`, or the
reachable host with the most free slots.

## Configure the receiving side

The target can have its own `~/.config/hev/dispatch.toml`. It is optional; with
none, the target admits every repository in its workspace. Settings here win
over anything the sender says.

```toml
workspace = "~/workspace"
notify = ["notify-command", "{reply}", "dispatch {name}: {state} {summary}"]

[admission]
repos = ["https://example.com/team/project.git"]

[hosts.buildbox]
local = true
cap = 8

[hosts.buildbox.env]
EXTRA_API_TOKEN = ""
```

- **`[admission] repos`** is the list of `origin` remotes this machine will run.
  It is read only from this file, before any fetch or worktree. A missing key
  admits all; `repos = []` admits none. See [admission](/docs/admission).
- **`[hosts.buildbox]`** must use the same name the sender uses. The target
  reads its `harness_wrapper` and `env` from this entry.
- **`[hosts.buildbox.env]`** adds environment variable names to forward to
  workers. Only the names are used; the values come from the target's own
  environment when the order is admitted. Common ones such as
  `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `GH_TOKEN` are forwarded already.
- **`notify`** runs on the target when a run ends. It is an argument list,
  run without a shell, with `{name}`, `{state}`, `{summary}` and `{reply}`
  filled in.

## Capacity

Each host takes at most `cap` runs. Admission reserves a slot under a short
lock on the target, so two senders cannot overfill it. A full host refuses
with `host full (n/cap)` and lists the hosts with free slots. Nothing waits in
line: send it elsewhere, or send it again later.

Size `cap` to what the machine can carry. Each run is a full agent session plus
whatever builds and tests it starts.
