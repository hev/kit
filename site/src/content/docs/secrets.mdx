kit runs a memory-only secrets cache inside the daemon (hevd). Secrets can
live in 1Password (`op://vault/item/field`) or Azure Key Vault
(`azkv://vault/secret`). Every process on a host that needs the same value
costs one request per TTL instead of one each. That matters because a
1Password service account's daily quota is shared by every machine that uses
it, and a vault throttles per request. This page is how to use the cache.

Everything below applies to both stores. Wherever an example shows an `op://`
reference, an `azkv://` one works the same way, and one command can mix them.
[Choose a provider](#choose-a-provider) compares the two stores, and
[Set up 1Password](#set-up-1password) and
[Set up Azure Key Vault](#set-up-azure-key-vault) walk through each one.
[Replace a secret on disk](#replace-a-secret-on-disk) shows a `.env` file
before and after.

## Why not a .env file

A `.env` file keeps the secret itself, in plain text, in the place a coding
agent works. That causes four problems.

- **An agent can read it, and what an agent reads can leave the machine.** An
  agent session can open any file its user can. A `.env` in the repo is one
  `cat` or `grep` away, and once the value is in the session it is in the
  model's context, the session transcript and the trace. kit captures traces
  and, with [kit + layer](/docs/kit-and-layer), shares them with the team.
- **It gets copied.** A `.env` rides along in a worktree copy, an `rsync` to
  a host, a container build context, a backup and, when `.gitignore` misses
  it once, a commit. Each copy holds the real value and nobody tracks them.
- **Every host needs its own copy.** A team dispatching to shared hosts ends
  up with the same key in a file on every machine and every teammate's
  laptop. Rotating it means finding and editing all of them, so it doesn't
  get rotated.
- **Nothing records who used it.** A file read leaves no trace. You cannot
  tell which job or agent took the key, or whether anything did.

A reference such as `op://vault/item/field` or `azkv://vault/secret` is not a
secret. It can sit in a script, a unit file, an order or a commit, and an agent
can read it without learning anything. The value stays in the vault, is
fetched when a program starts, and exists only in the daemon's memory and
that program's environment. Rotation is one change in the vault, access is
the vault's own permissions, and every real request is in
[the read log](#the-read-log) with the caller's name.

A reference does not hide the value from the program that uses it, or from an
agent that runs that program and prints its environment. It removes the copy
at rest, which is the one that leaks.

## The one rule

Read through `hev secrets`. Don't run `op read`, `op inject` or `op run`
yourself, in a script, a wrapper, a shell profile or an agent session.

| You need | Use |
| --- | --- |
| One value in a shell variable | `x=$(hev secrets read --label NAME --ttl 1h op://vault/item/field)` |
| Several variables in the current shell | `eval "$(hev secrets env --ttl A=1h --ref A=op://… --ref B=op://…)"` |
| Values in a program's environment | `hev secrets run --ref A=op://… --ttl A=1h -- program args` |
| Values for a program, as JSON on a pipe | `hev secrets env --format json --ref A=op://…` |
| What the host is spending | `hev secrets status` (`--no-quota` asks 1Password nothing) |
| Whether the cache is up, for free | `hev secrets ping` (exit 0 up, 69 not) |
| Each value's provenance, for a wrapper's log | `--explain` on stderr, or `env --format json-detail` |

Values come back only through a pipe or the child's environment. Nothing is
written to disk, a log or a process argument; the reference is the only
argument. `--ttl` is how long the daemon may reuse a value: five minutes by
default, at most 24 hours, and `0s` forces a fresh read. Choose the longest
TTL your rotation allows. An hour suits most API keys.

### Exit codes

| Exit | Meaning |
| --- | --- |
| 0 | The value was delivered. |
| 75 | Rate limited. The retry time is on stderr. |
| 69 | `--cache-only` (or `ping`): no daemon serves this account. |
| 78 | `--direct-status`: the value was delivered, but by a direct read, not the cache. |

On exit 75, **make one attempt and stop**. Don't loop, sleep and retry, or
fall back to `op`. The cache already refuses to send another request before
the retry time, and a second path around it is how one host empties the
account for everyone.

Don't put a loader that resolves many secrets in a shell profile. Source it in
the job that needs the values.

## Choose a provider

The reference's scheme picks the store. Both stores get the same cache, TTL
limit, batching, one-attempt rule on rate limits, cooldown and read log.

| Reference | Store |
| --- | --- |
| `op://vault/item/field` | 1Password, through a service account (`op` on PATH) |
| `azkv://VAULT/SECRET` | Azure Key Vault at `https://VAULT.vault.azure.net`, latest version |
| `azkv://VAULT/SECRET/VERSION` | a pinned version (32 hex digits) |
| `azkv://VAULT.vault.usgovcloudapi.net/SECRET` | a sovereign cloud's vault (also `vault.azure.cn`). The token audience and sign-in host follow the suffix. |

Use whichever store already holds the secret. A host needs nothing for a store
it doesn't use: a Key Vault-only host needs no `op` and no 1Password token, and
a 1Password-only host needs no Azure settings. A vault behind a private
endpoint keeps its ordinary name. Vault and secret names follow Key Vault's
own rules, and anything else in a reference (a port, a query, an extra path
segment, a trailing slash) is refused.

### The Key Vault role

The Azure identity kit signs in as needs to get secrets and nothing more.
Give it the built-in role **Key Vault Secrets User**, scoped to the vault
(Azure RBAC). On a vault that still uses access policies, grant only the
secret permission *Get*. kit never lists, sets or deletes secrets.

### Key Vault credentials

kit never signs in interactively: there is no browser or device-code prompt.
With no credential configured, the error names what to set. Set one of these
in the daemon's environment:

| Credential | Settings |
| --- | --- |
| Managed identity, Azure VM | `HEV_AZKV_CREDENTIAL=managed-identity` (plus `AZURE_CLIENT_ID` for a user-assigned identity) |
| Managed identity, Azure Arc server | Nothing. The Arc agent sets `IDENTITY_ENDPOINT` and `IMDS_ENDPOINT`; the user must be in the agent's token group. |
| Managed identity, App Service | Nothing. The platform sets `IDENTITY_ENDPOINT` and `IDENTITY_HEADER`. |
| Workload identity (Kubernetes) | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_FEDERATED_TOKEN_FILE` |
| Service principal with a certificate | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_CERTIFICATE_PATH` (a PEM with the certificate and an unencrypted RSA key, readable only by the user) |
| Service principal with a client secret | `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and `AZURE_CLIENT_SECRET_REF=op://…` (read through the cache) or `AZURE_CLIENT_SECRET` |
| An existing `az login` | `HEV_AZKV_CREDENTIAL=azure-cli`. kit runs `az account get-access-token`, never `az login`. A convenience for a workstation. |

Without `HEV_AZKV_CREDENTIAL`, kit picks a client secret, then a certificate,
then workload identity, then a platform identity endpoint. The VM metadata
endpoint and `az` are used only when named, so a host outside Azure never
waits on a metadata probe and never borrows a developer's login by accident.
`HEV_AZKV_CREDENTIAL` accepts `auto`, `client-secret`, `client-certificate`,
`workload-identity`, `managed-identity` and `azure-cli`.

Set the same variables in the environment of the callers that use the
daemon. The daemon serves a Key Vault request only when the caller holds the
same credential (see [Switch the cache on](#switch-the-cache-on)).

For an Azure Stack Hub vault, list its DNS suffix in `HEV_AZKV_DNS_SUFFIXES`
(comma separated) and set `AZURE_AUTHORITY_HOST` to its sign-in host, an
https URL.

Prefer a credential with no secret: a managed identity (on an Azure VM or an
Arc-connected server, Windows included) or workload identity. Otherwise use a
certificate. Never put a client secret in a unit file, a scheduled task or a
profile. Point `AZURE_CLIENT_SECRET_REF` at a reference instead, and the daemon
reads it through its own cache. A reference back to `azkv://` is a cycle and
is refused. Access tokens stay in the resolving process's memory and are
never written anywhere.

### A Windows host with only Key Vault

Run hevd (or `hev daemon --secrets-only`) with one of:

- on an Azure VM: `HEV_AZKV_CREDENTIAL=managed-identity`
- on an Arc-connected server: nothing beyond Arc's own variables
- elsewhere: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and
  `AZURE_CLIENT_CERTIFICATE_PATH`

It needs no `op`, no `OP_SERVICE_ACCOUNT_TOKEN` and no token file. Callers use
the same commands with `azkv://` references:

<CodeTabs>

```powershell
$env:DB_PASSWORD = hev secrets read --label DB_PASSWORD --ttl 1h azkv://VAULT/SECRET
hev secrets run --ref DB_PASSWORD=azkv://VAULT/SECRET --ttl DB_PASSWORD=1h -- program.exe
```

## Switch the cache on

The cache serves a caller when both hold the same service-account token, taken
from `OP_SERVICE_ACCOUNT_TOKEN` or else the token file `HEV_OP_TOKEN_FILE`
(default `~/.config/op/token`, which must be mode 0600). A host whose token is
in that file needs no configuration: start or restart hevd. To use a different
file, set it in the daemon's service:

<CodeTabs>

```ini
# ~/.config/systemd/user/hevd.service.d/secrets.conf
[Service]
Environment=HEV_OP_TOKEN_FILE=%h/.config/op/token
```

```text

Never put the token itself in the file. Run `systemctl --user daemon-reload` and `systemctl --user restart hevd`. Verify with `hev secrets ping`, which should print `up` and exit 0.
Docs: https://hevkit.com/docs/secrets#switch-the-cache-on (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

A host that doesn't run hevd can run the endpoint on its own with
`hev daemon --secrets-only`. The repository's `staged/host-secrets/` directory
has a systemd unit and a launchd job for that. The Linux unit:

<CodeTabs>

```ini
# ~/.config/systemd/user/hev-secrets.service
[Unit]
Description=hev Kit local secrets cache (memory only)

[Service]
Type=simple
ExecStart=%h/.local/bin/hev daemon --secrets-only
Environment=HEV_OP_TOKEN_FILE=%h/.config/op/token
Restart=on-failure
RestartSec=60
UMask=0077

[Install]
WantedBy=default.target
```

| Variable | Effect |
| --- | --- |
| `HEV_SECRETS_ENDPOINT` | Moves the endpoint, for the daemon and its callers alike: an absolute socket path on Linux and macOS (its directory must be 0700), `\\.\pipe\NAME` on Windows. Unset, it is `~/.hev/secrets/agent.sock` or `\\.\pipe\hev-secrets-<SID>`. |
| `HEV_SECRETS_CACHE=off` | This process skips the cache, for a test that uses a fixture `op`. |
| `HEV_SECRETS_READ_LOG` | Moves the read log; `off` disables it. |
| `HEV_SECRETS_COOLDOWN` | Moves the cooldown file; `off` disables it (tests only). |

The daemon serves each store separately. It answers a request when, for every
store the request names, the caller and the daemon hold the same credential:
the same 1Password token, or the same Azure credential type, tenant, client
and secret or certificate. Only SHA-256 fingerprints cross the endpoint. A
caller whose Azure settings differ from the daemon's still gets its 1Password
reads served, and reads Key Vault directly. Upgrade hevd before callers start
using `azkv://`, because an older daemon refuses those references.

With no endpoint, `hev secrets` still batches and logs, but each process
pays for its own request, and `hev secrets status` says `daemon: unavailable`.

## Set up 1Password

### Prerequisites

- A 1Password service account with read access to the vaults you need, and
  its token. kit never uses the 1Password desktop app or biometric unlock.
- The `op` CLI on the PATH of the daemon and of every caller.
- hev on the host with hevd running ([Install](/docs/install)), or the
  secrets-only endpoint from [Switch the cache on](#switch-the-cache-on).

### 1. Put the token in the token file

Keep the token in `~/.config/op/token`, so the daemon and every caller use the
same one without it appearing in a unit file or a profile. kit ignores the
file if its mode grants anything to group or others.

<CodeTabs>

```sh
mkdir -p ~/.config/op
chmod 700 ~/.config/op
touch ~/.config/op/token
chmod 600 ~/.config/op/token
# paste the service-account token into ~/.config/op/token with an editor
```

### 4. Verify 1Password

- `--explain` prints one line per reference on stderr, such as
  `hev secrets: DB_PASSWORD source=read via=daemon`. `source=read` means the
  call made a real request, `source=cache` means it was served from memory,
  and `via=direct` means no daemon served it.
- Run the same read again. It should say `source=cache`.
- `hev secrets status --no-quota` shows a 1Password row with the credential
  `service-account token (token file)` or
  `service-account token (environment)`.

### 1Password failures

| Message or symptom | Cause and fix |
| --- | --- |
| `1Password service-account token is required; desktop unlock disabled` | No token in `OP_SERVICE_ACCOUNT_TOKEN` and no usable token file. Check `HEV_OP_TOKEN_FILE` or `~/.config/op/token`, and that its mode is 0600. |
| `hev secrets: notice: fallback to direct 1Password read` on stderr | No daemon serves this account. Restart hevd, and check that the daemon and the caller use the same token. |
| `hev secrets ping` prints `unavailable` | The same cause as the notice above. |
| `1Password secret resolution failed (service account required; desktop unlock disabled)` | `op` could not resolve a reference: a wrong vault, item or field, or a service account without access to that vault. |
| Exit 75 | The account is rate limited. Wait for the time on stderr. See [After a rate limit](#after-a-rate-limit). |

## Set up Azure Key Vault

### Prerequisites

- A vault, the names of the secrets you need, and an identity that has the
  role in [The Key Vault role](#the-key-vault-role).
- One credential for that identity from
  [Key Vault credentials](#key-vault-credentials).
- hev on the host with hevd running ([Install](/docs/install)), upgraded
  before any caller uses `azkv://`. Neither `op` nor the Azure CLI is needed,
  unless you choose `HEV_AZKV_CREDENTIAL=azure-cli`.

### 1. Configure the daemon

Put the credential's variables in hevd's environment. On Linux with a
certificate, as a systemd drop-in:

```ini
Environment=AZURE_TENANT_ID=TENANT_ID
Environment=AZURE_CLIENT_ID=CLIENT_ID
Environment=AZURE_CLIENT_CERTIFICATE_PATH=%h/.config/azkv/client.pem
```

### Key Vault failures

| Message | Cause and fix |
| --- | --- |
| `Azure Key Vault has no credential configured; ...` | No credential is set. The message names every variable that would set one. |
| `Azure Key Vault denied access (HTTP 403): the ... principal needs get on secrets for this vault` | Give the identity the role in [The Key Vault role](#the-key-vault-role). |
| `Azure Key Vault refused the ... credential (HTTP 401)` | The vault refused the access token. Check the tenant and client IDs. |
| `Azure Key Vault has no such secret or version (HTTP 404)` | Check the secret name and, for a pinned reference, the version. |
| `Azure sign-in failed for the ... credential (HTTP ...)` | The sign-in endpoint refused the client secret, certificate or federated token. |
| `Azure client certificate: the PEM file needs a certificate and an unencrypted RSA private key` | Convert the certificate to that form. PFX and password-protected files are not read. |
| `Azure CLI credential selected but az is not on PATH` | Install the Azure CLI for the daemon's user, or choose another credential. |
| `Azure Key Vault managed identity: IDENTITY_ENDPOINT needs IDENTITY_HEADER (App Service) or IMDS_ENDPOINT (Azure Arc)` | A partial platform identity environment. Set the missing variable, or name a credential with `HEV_AZKV_CREDENTIAL`. |
| `Azure Arc identity key file is unreadable (the user must be in the agent's token group)` | Add the daemon's user to the Arc agent's token group. |
| `Azure Key Vault: AZURE_CLIENT_SECRET_REF cannot be an azkv:// reference (credential reference cycle); use another provider` | Keep the client secret in another store, such as 1Password. |
| `set AZURE_AUTHORITY_HOST for a vault outside Azure's known clouds` | An Azure Stack Hub vault. Set `AZURE_AUTHORITY_HOST` and `HEV_AZKV_DNS_SUFFIXES`. |
| Exit 75 | The vault throttled the request (HTTP 429). See [After a rate limit](#after-a-rate-limit). |

## Replace a secret on disk

value, and put a reference under the same name:

<CodeTabs labels={["1Password", "Azure Key Vault"]}>

```sh

# STRIPE_API_KEY=sk_live_EXAMPLE_VALUE
STRIPE_API_KEY=op://VAULT/ITEM/FIELD
```

```sh
# .env
# STRIPE_API_KEY=sk_live_EXAMPLE_VALUE
STRIPE_API_KEY=azkv://VAULT/stripe-api-key
```

`hev secrets run` reads the file, resolves every value that is an `op://` or
`azkv://` reference through the cache, and starts the program with the
results in its environment. Lines with ordinary values, such as a port or a
hostname, pass through unchanged, and commented lines are ignored. One file
can mix both stores. Without a file, `--ref NAME=REF` does the same for one
variable.

Three things make the swap complete:

1. **Store the value first.** kit only reads secrets, so put the value in the
   vault with the vault's own tools before you edit the file. In 1Password,
   add it as a field on an item the service account can read and use *Copy
   Secret Reference* to get the `op://` reference. In Key Vault, names allow
   letters, digits and hyphens only, so `STRIPE_API_KEY` becomes
   `stripe-api-key`.
2. **Check the reference.**
   `hev secrets read --label STRIPE_API_KEY --explain REF | wc -c` prints a
   byte count above zero when the store, the credential and the reference are
   right, without showing the value.
3. **Delete the commented line and rotate the key.** Once the program runs
   from the reference, remove the commented line. The old value sat in a file
   that agents, backups and copies could reach, so rotate it at its issuer
   and store the new value under the same name. Nothing else changes: the
   file keeps the same reference.

A `.env` file that holds only references and ordinary settings has no secret
in it. It can be committed, copied to a host and read by an agent.

## kit's own reads

kit reads its own secrets through the same cache:

- **The hev layer key.** `HEVLAYER_API_KEY_REF` (`op://` or `azkv://`; the
  older `HEVLAYER_API_KEY_OP_REF` still works) is read through the daemon
  with a six-hour TTL by hevd, `hev board serve` and every other command that
  needs the key.
- **The native gate.** Its database references are resolved in one batch with
  a one-hour TTL. They may be `azkv://` references, read through `hev`, which
  must be on PATH.

With no daemon, each reads directly as before. A direct read is never silent.
It prints one line on stderr starting
`hev secrets: notice: fallback to direct 1Password read`, with the reason. Any
answer from the daemon is final, a rate limit included, so kit never retries
it directly.

## The read log

Every real request appends one line to `~/.hev/secrets/op-reads.log` (mode
0600; the name predates Key Vault). Cache hits don't, because they cost
nothing.

```text
2026-11-11T21:31:02Z caller=bash[4121]>hev_secrets_read kind=inject refs=1 labels=DB_PASSWORD#9f2c11ab outcome=ok provider=op
2026-11-11T21:31:05Z caller=bash[4121]>hev_secrets_run kind=get refs=2 labels=DB_USER#04be71d2,DB_PASSWORD#5a1c9e30 outcome=ok provider=azkv
```

Each line has the time (UTC), the caller (`--caller`, `HEV_SECRETS_CALLER`,
or the parent command), the kind of request (`inject`, `read` or `ratelimit`
for 1Password, `get` for one Key Vault batch), how many references, the
labels, the outcome and the provider. A label is the variable name plus the first eight hex digits
of the reference's SHA-256. Find a label with
`printf %s op://vault/item/field | sha256sum | cut -c1-8`. The log never holds
a value, a token or a reference, and it rotates at 4 MiB.

When the account runs out, find the heaviest callers:

<CodeTabs>

```sh
hev secrets status
awk '{print $2}' ~/.hev/secrets/op-reads.log | sort | uniq -c | sort -rn | head
grep 'provider=azkv' ~/.hev/secrets/op-reads.log | grep -c rate_limited   # a throttled vault
```

## After a rate limit

The first rate-limit answer starts a cooldown for the whole host. Its limit
class and reset time, and nothing else, go to `~/.hev/secrets/op-cooldown.json`
beside the read log. Until the reset, every kit process on the host gets the
same error and sends nothing. That covers the daemon, a restarted daemon,
`hev secrets` with no daemon, the hev layer key and the native gate. hevd
stays up and keeps serving cached secrets while its own key waits for the
reset, instead of exiting into a restart loop. The first successful request
after the reset deletes the file.

The cooldown is per store. Key Vault answers a throttled request with HTTP 429
and `Retry-After`. kit makes that one request, honours `Retry-After`, and
records the cooldown in `azkv-cooldown.json` in the same directory. A throttled
vault never holds back 1Password reads, and a spent 1Password account never
holds back Key Vault. A request that mixes both fails as a whole, before
asking either store, when either is in cooldown.

<Callout label="Don't">
Don't delete the cooldown file to unstick a host. The account is still out,
and the next request only spends more of it. A file that is malformed or
claims more than 24 hours is ignored.
</Callout>

## Status

`hev secrets status` (`--json` for programs) shows:

- one row per store: credential type (never a value or identifier),
  reachability from its last real request, hits, misses, requests and any
  cooldown. An unconfigured store says what to set.
- whether the daemon is up, and since when
- cache hits and misses
- real requests since start, and how many were rate limited
- the active cooldown and its retry time
- the read log's 24-hour count
- the 1Password account's quota rows and their reset times, checked at most
  every five minutes and never during a cooldown. `--no-quota` skips this
  check. Key Vault has no quota endpoint, and status says so.
