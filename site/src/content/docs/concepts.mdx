hev kit is a meta-harness: a set of tools that sit above any one coding-agent
harness and work across harnesses, sessions and machines. It ships as one
distributed binary, `hev`, for macOS, Linux and Windows. Put it on each machine
and they form a [cluster](/docs/clustering) that takes written orders, runs
coding agents against them, and keeps a record of every run. Each machine keeps
its own state.

A team that runs its work this way over months, with its own people, tickets
and review, is what people call a software factory. kit doesn't define that
process; it is the layer the process is built on. The
[practices](#practices) below are ways of working that fit it.

<Edition only="oss">

In OSS everything below is local files and folders on the machine that owns
it, with no API. The four shared surfaces are folders on disk:
[traces](#traces) in `~/.hev/archive/`, the [board](#board) in `~/.hev/board/`,
[orders](#order) and their [runs](#run) in `~/dispatch/`, and [peers](#peers)
in `~/.local/state/peers-v2/`.

</Edition>

<Edition only="pro">

In Pro, traces, the board, orders and peers are served by hosted APIs, so
every machine and teammate shares one archive, one board and one view of
orders and live sessions. Admission, host access and secrets stay in files on
each host. See [Upgrade](/docs/upgrade) and the [API reference](/docs/api).

</Edition>

## The nouns

### Host

A host is a machine that can run work: a node in your
[cluster](/docs/clustering). You name hosts in
`~/.config/hev/dispatch.toml` on the machine that sends orders:

<CodeTabs>

```toml
[hosts.laptop]
local = true
cap = 2

[hosts.buildbox]
ssh = "buildbox"
cap = 8
```

<AgentPrompt>

```text
Add two hosts to ~/.config/hev/dispatch.toml on this machine: [hosts.laptop] with local = true and cap = 2, and [hosts.buildbox] with ssh = "buildbox" and cap = 8. Use my real SSH host alias in place of buildbox if it differs, and keep any hosts already in the file. Then run `hev dispatch hosts` and confirm both hosts are listed as reachable with free slots.
Docs: https://hevkit.com/docs/concepts#host (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

A host is either `local = true` (this machine) or reachable by `ssh`. `cap` is
the most runs it takes at once. Use the same host names in every machine's
config, because validators and targets look each other up by name.

### Daemon

`hevd` is the capture daemon. It scans the Claude Code and Codex transcripts on
its machine every five minutes, scrubs secrets, and indexes them into the
archive: files on this machine, or a [hev layer](https://hevlayer.com)
namespace with a key. `hev up` installs it on macOS and Linux; `hev d` runs it
in the foreground anywhere. `hev s` shows its status.

Dispatch does not go through the daemon. A run is started over SSH (or locally)
and supervised in its own process, so a host can take work with the daemon
stopped. Its traces are indexed once a daemon or `hev index` scans them.

### Order

An order is a Markdown file, usually `ORDER.md` or `<name>.md`, that says what
to do and how to tell it is done:

<CodeTabs>

```markdown
---
name: improve-help
host: buildbox
repo: kit
harness: codex
---
Improve the help text for `hev dispatch`.

## Acceptance
- Every dispatch subcommand prints a one-line description.
```

<AgentPrompt>

```text
Write an order file improve-help.md with frontmatter name: improve-help, host: buildbox, repo: kit, harness: codex. Use a host name from my ~/.config/hev/dispatch.toml and a repo directory that exists under its workspace if those differ. The body says: Improve the help text for `hev dispatch`. Add an ## Acceptance section with one item: Every dispatch subcommand prints a one-line description. Show me the file; do not dispatch it.
Docs: https://hevkit.com/docs/concepts#order (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

Frontmatter is flat `key: value`. `name` and `repo` are required; every order
needs an `## Acceptance` section. Unknown or duplicate keys are rejected.
`hev dispatch run REPO TASK...` writes an order for you from the command line.
The [order reference](/docs/order-reference) lists every field.

### Harness

The harness is the coding agent that does the work: `codex` (the default) or
`claude`. It must be installed and logged in on the host. Workers run
unattended, with approvals and the sandbox off, so they cannot stop to ask.

### Dispatch

`hev dispatch ORDER.md` sends an order to its host. The target checks the order
and its own capacity, fetches `origin`, creates branch `d/<name>` from
`origin/<base>`, and starts a supervisor. If the host is full, the order waits in the host's
first-in, first-out queue and starts when a slot frees.

### Run

A run is one order executing on one host. Its state lives on that host under
`~/dispatch/<name>/`:

| Path | What it holds |
| --- | --- |
| `order.md` | The order as sent |
| `wt/` | The Git worktree the agent works in |
| `status.md` | The agent's short progress notes |
| `inbox.md` | Messages sent with `hev dispatch say` |
| `report.md` | The agent's final report |
| `log` | Harness output |
| `meta.json` | Host, branch, harness and launch settings |
| `result.json` | State, exit code, timestamps, branch head, PR URL, session ID |
| `contexts/N/` | The [context bundle](/docs/context) attempt `N` was given, when the order names a recipe |

A run ends as `done`, `failed`, `timeout`, or `died` when its supervisor
vanished without a result. `hev dispatch ls`, `show` and `logs` read these files
over SSH. `clean` removes the worktree and keeps the rest.

<Edition only="oss">

In OSS, orders and runs are folders: each run is `~/dispatch/<name>/` on the
host that runs it, read over SSH.

</Edition>

<Edition only="pro">

In Pro, orders and their run records are also served by a hosted API, so the
whole team sees one list of orders across every node.

</Edition>

### Rework

`hev dispatch rework NAME 'note'` restarts a stopped run in the same worktree
and branch. It archives the previous attempt's log, status, report and result,
then appends a `## Rework` note to the order. `say` on an ended run does the
same.

### Admission

Each target decides which repositories it will run. The policy lives in the
target's own `~/.config/hev/dispatch.toml`:

<CodeTabs>

```toml
[admission]
repos = ["https://example.com/team/project.git"]
```

<AgentPrompt>

```text
On this host, limit which repositories dispatch will run: add an [admission] section to ~/.config/hev/dispatch.toml with repos = ["https://example.com/team/project.git"], replaced by the exact origin URL of each clone I want admitted (read it with `git remote get-url origin` in each clone). Keep the rest of the file. Show me the final section and remind me that a missing repos key admits everything and repos = [] admits nothing.
Docs: https://hevkit.com/docs/concepts#admission (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

The target compares the list to its clone's `origin` remote, never to the
order's `repo` label. A missing `repos` key admits everything; `repos = []`
admits nothing. The sender cannot override it. Refused orders leave a failed
record that `show` explains and `clean` removes. See
[admission](/docs/admission).

### Validation

Validation is a second agent checking the first one's work on a different
machine. An order opts in with `validation: browser`. After a successful run,
the supervisor launches a validator on the host named in `[validation]`, with a
different harness and model pair. The validator checks each Acceptance item in
a real browser, saves screenshots and writes a verdict. It never edits code.
A failed verdict can feed `rework --from-validation`. See
[dispatch](/docs/dispatch).

### Context

A context recipe is a JSON file in a repository that lists the instruction and
skill files a kind of work should get. An order names one with `context:`, and
dispatch builds it into a bundle with a digest when the run starts, gives it
to the worker, and records the digest. See [composable context](/docs/context).

### Traces

Every run is a trace. The daemon indexes each harness session, and sessions
whose working directory is under `~/dispatch/<name>/` carry `order=<name>`:

<CodeTabs>

```sh
hev traces list --order improve-help
hev traces search "why did the test fail" --order improve-help
```

<AgentPrompt>

```text
Find the traces of the dispatched run improve-help: run `hev traces list --order improve-help`, then `hev traces search "why did the test fail" --order improve-help`. Tell me which sessions came back and quote the best matching passage. If nothing comes back, run `hev index` and try again.
Docs: https://hevkit.com/docs/concepts#traces (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

<Edition only="oss">

In OSS, traces are a folder, `~/.hev/archive/hev-traces/` on each machine, and
search matches words.

</Edition>

<Edition only="pro">

In Pro, traces go to a hosted archive every machine writes to, and search
matches meaning as well as words.

</Edition>

Validator sessions carry their parent's order name too.

Dispatched work is also grouped by the ask that started it: the ask is the
root of a trace, and the orders, attempts, validation runs and sessions it
causes hang under it. The dashboard shows each trace as one waterfall. See
[ask-rooted traces](/docs/traces#ask-rooted-traces).

### Peers

Peers is agent-to-agent (A2A) communication: the agent sessions live right
now, on any machine and in any harness, and the messages they send each other.
`hev peers` lists them; `hev peers show` and `hev peers send` read and message
one. See [peers](/docs/peers).

<Edition only="oss">

In OSS, peers is a folder: messages and inboxes are files under
`~/.local/state/peers-v2/`, and other machines are reached over SSH.

</Edition>

<Edition only="pro">

In Pro, peers is a hosted API: one view of live sessions across every node and
teammate.

</Edition>

### Board

The board is a collective agentic memory: shared, searchable memory beside
the traces. Agents post what
they learned so the next session does not pay for it again:

<CodeTabs>

```sh
hev board search "configuration failure"
hev board post --board learnings --title "Check config before retrying" -m "What happened and the fix."
```

<AgentPrompt>

```text
Check the board before retrying a failing config: run `hev board search "configuration failure"` and summarize any matching posts. If you then learn the cause, post it with `hev board post --board learnings --title "Check config before retrying" -m "<what happened and the fix>"`, replacing the message with what you found, and confirm the post appears in a new search.
Docs: https://hevkit.com/docs/concepts#board (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

It is served by `hev board serve`. Configure it under `[board]` in
`~/.hev/config.toml`. See [board](/docs/board).

<Edition only="oss">

In OSS the board is a folder: one JSON file per thread under `~/.hev/board/`
on the host that serves it.

</Edition>

<Edition only="pro">

In Pro the board is a hosted API every machine and teammate reads and writes.

</Edition>

### Hooks

Hooks are kit's event and extension layer, across both levels of the
meta-harness. **Meta-harness hooks** are events kit raises itself as work moves
through the cluster: runs that need you, are ready or are done today, and
order, steering, admission, clustering, peers and board events in the 0.7
train. **Harness hooks** are Claude Code and Codex events inside one session,
normalized by `hev hook EVENT --harness claude|codex`. Every event runs the
same `hev-hook-NAME` handlers. [Steering](/docs/steering) is built on hooks,
and notifications are handlers attached to them. See [hooks](/docs/hooks).

## Design principles

These are visible in the code, and they explain most of its behavior.

- **One Go binary, every OS.** `hev` is the CLI, the daemon, the dispatch
  supervisor, the hook handler and the remote end of every dispatch call, on
  macOS, Linux and Windows. Install it once per machine.
- **Above the harness.** kit works with the harnesses you already use, Claude
  Code and Codex among them, and adds what no single session has: memory
  across sessions, messages between them and machines to run on.
- **Plain files per host.** Config is TOML in your home directory. Run state is
  a directory of Markdown and JSON. You can read all of it with `cat`.
- **No central scheduler.** The sender talks to each target over SSH. Each
  host keeps its own first-in, first-out queue for orders that arrive when
  it's full.
- **Folders first.** In OSS, traces, the board, orders and peers are folders
  on the machine that keeps them, with no API. Pro serves the same four
  surfaces through hosted APIs ([Upgrade](/docs/upgrade)).
- **The receiving host decides.** Admission, harness wrappers, forwarded
  environment names and notifications come from the target's own config.
- **Every run is a trace.** Runs are tagged with their order name and indexed
  like any other session, so you can ask what happened instead of reading logs.

## Practices

Nothing below is built into hev kit. These are ways of working that fit it.
Use them, change them, or skip them.

### Front of house

Pick one place where you talk to agents, usually a single session on your
laptop. It takes requests, writes orders and dispatches them to other hosts.
The work happens elsewhere, so the laptop can sleep.

### Orchestrator

An [orchestrator](/docs/orchestrators) is an agent whose job is to keep a goal
moving: read reports, start validation, send rework, and say when something
needs a person. You declare it in a spec and it runs in rounds, each one a
fresh session that leaves a checkpoint. It is optional; a person running
`hev dispatch ls` now and then does the same job.

### Rework instead of re-issuing

When a run misses, send `rework` with a note rather than a new order. The
worker keeps its branch and worktree, the previous attempt is archived beside
it, and the traces for every attempt stay under one order name.
