Hooks are kit's event and extension layer. They cover two layers:

1. **Meta-harness hooks**, across the cluster. kit raises these itself as work
   moves through the system: an order is queued, a run needs you, a steer is
   acknowledged, a node joins, a peer comes online, someone posts to the board.
2. **Harness hooks**, inside one agent session. Claude Code and Codex each have
   their own hook system with their own event names, JSON and answers. kit
   normalizes both into one set of events: `hev hook EVENT --harness claude|codex`.

Both layers feed the same handlers. You write a `hev-hook-NAME` executable
once, and it can react to a tool call inside a session as well as to a run
finishing on another node. [Steering](/docs/steering) is built on this layer.
[Notifications](#notifications) are handlers attached to its events: Slack,
your own scripts and webhooks.

<Callout label="What fires today">
All six harness events fire today, and so do three meta-harness events:
`needs-you`, `ready` and `done`. The other meta-harness events (`order-*`,
`steer-*`, `admission-*`, `cluster-*`, `peer-*` and `board-*`) are being wired
in during the 0.7 train. The tables below mark each one **Live** or **0.7**.
Handlers written for the live events will receive the new ones as they land,
without changes.
</Callout>

## One handler model

Every event takes the same path, whether a harness or kit raised it:

1. **Normalize.** The event becomes one JSON envelope, `hev.hook.event/v1`,
   naming the event, where it came from (`claude`, `codex` or `kit`) and its
   payload.
2. **Log.** A redacted copy is appended to `~/.hev/hooks/events.jsonl`.
3. **Handle.** The built-in handlers and every `hev-hook-NAME` on PATH run
   concurrently under one time budget, and the
   [fail-open](#fail-open) rules apply.

Handlers get the event name as their first argument and in `HEV_HOOK_EVENT`,
the source in `HEV_HOOK_HARNESS` (`kit` for meta-harness events) and the
event JSON on stdin. A handler that only cares about some events checks its
first argument and exits quietly for the rest.

Harness events go through all three steps today. The live meta-harness
events (`needs-you`, `ready`, `done`) run the same handlers under the same
budget and kill switch, but their stdin body is the attention notice
(`hev.attention.event/v1`, shown [below](#the-notice)) and they are not yet
written to `events.jsonl`. Moving them onto the common envelope and log is
part of the 0.7 work.

## Meta-harness hooks

kit raises these on the node where the moment happens. A handler on that
node sees them, and a handler that posts to Slack or a webhook turns them into
a notification.

### Dispatch and orders

| Event | Raised when | Status |
| --- | --- | --- |
| `needs-you` | A run or orchestrator asks a person to decide something, or a steering halt escalates to a hard stop. | Live |
| `ready` | A run's PR is ready with all checks green, or an orchestrator meets its goal. | Live |
| `done` | A run or orchestrator ends any other way. | Live |
| `order-queued` | An order is accepted and waits for a worker slot. | 0.7 |
| `order-started` | A queued order launches its harness. | 0.7 |
| `order-rework` | A run is sent back with `hev dispatch rework` or `say`. | 0.7 |

The three live events are described under [Notifications](#notifications).
See [Dispatch](/docs/dispatch) and [Orders](/docs/orders).

## Harness hooks

Every hook Claude Code or Codex runs is the same command:

```sh
hev hook EVENT --harness claude|codex
```

The harness passes its hook JSON on stdin. kit normalizes it to
`hev.hook.event/v1`, logs it, runs the handlers, and answers in the harness's
own shape. A handler you write once works in both harnesses.

| Event | Claude Code / Codex name | Handlers can | Status |
| --- | --- | --- | --- |
| `session-start` | `SessionStart` | add context | Live |
| `prompt-submit` | `UserPromptSubmit` | add context, or halt (refuse the prompt) | Live |
| `pre-tool` | `PreToolUse` | block the call with a reason, or halt | Live |
| `post-tool` | `PostToolUse` | add context, or halt | Live |
| `stop` | `Stop` | observe | Live |
| `pre-compact` | `PreCompact` | observe | Live |

Codex sends Claude-compatible JSON (plus `turn_id`); its tools are `Bash` and
`apply_patch`. pi is not supported: `--harness pi` is refused, and the only
message that reaches a pi session is a `peers send` note.

### Install the harness hooks

Dispatch runs and orchestrator rounds need nothing installed: their
supervisor wires the hooks for that one launch and points them at the run.
Interactive sessions need the hooks in the harness's settings:

<CodeTabs>

```sh
hev hooks install                  # every harness home that exists
hev hooks install --harness claude
hev hooks check                    # non-zero when missing or stale
hev hooks uninstall                # removes only kit's entries
```

<AgentPrompt>

```text
Install kit's hooks for my interactive Claude Code and Codex sessions: run `hev hooks install`, then `hev hooks check` and confirm it exits 0. Tell me which settings files it changed (~/.claude/settings.json, ~/.codex/hooks.json) and that a backup ending in .before-hev-hooks was written. If Codex is installed, remind me to open `codex` and trust the new hook once with /hooks; do not try to write that trust yourself.
Docs: https://hevkit.com/docs/hooks#install-the-harness-hooks (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

- Claude Code's hooks go in `~/.claude/settings.json`; Codex's in
  `~/.codex/hooks.json` (`$CODEX_HOME`).
- Install merges. Other hooks and settings are kept, the file mode is kept,
  and the previous file is saved as `settings.json.before-hev-hooks`. Each kit
  command ends in `--installed-by kit`; `check` and `uninstall` only touch
  commands with that stamp. Installing twice changes nothing; installing from a
  new binary repairs kit's entries in place.
- When a run's own hooks and the installed hooks would both fire, the
  installed copy steps aside, so nothing is handled twice.
- Codex runs a global hook only after a person trusts it: open `codex` and
  review it with `/hooks`. kit never writes that trust record.
- `hev skills sync` and `hev update` repair kit's entries where they are
  already installed. They never install hooks nobody asked for.

## Handlers

Two handlers are built in:

- **`steer`** finds the steering target (a dispatch run, an orchestrator or a
  local peers session) and delivers [steering](/docs/steering) messages at the
  next turn or tool call.
- **`peers-inbox`** injects the session's bound [peers](/docs/peers) inbox on
  `prompt-submit`.

Your own handlers are executables named `hev-hook-NAME` on PATH, found like
[exec commands](/docs/exec-commands): first match per name, `.exe` or `.cmd` on Windows.
Each gets the event name as its argument, the full event JSON on stdin, and
`HEV_HOOK_EVENT` and `HEV_HOOK_HARNESS` in its environment. It prints nothing
to continue, or one JSON object:

```json
{"decision": "continue|block|halt", "reason": "shown to the model", "context": "injected", "system_message": "shown to the person"}
```

Handlers run concurrently. When they disagree, halt beats block beats
continue, and contexts are joined in handler order. A handler that refuses
force pushes:

<CodeTabs>

```sh
#!/bin/sh
# hev-hook-no-force-push
case "$(cat)" in
  *'"kind":"mutate"'*'push --force'*) echo '{"decision":"block","reason":"No force pushes here."}' ;;
esac
```

## Fail open

A broken kit must never stop an agent.

- Every handler runs under one budget, `[hooks] timeout` (default `2s`). A
  handler that errors, exits non-zero, prints invalid JSON or misses the
  budget is dropped, with a warning in `~/.hev/hooks/warnings.log`, and its
  process group is killed.
- `hev hook` always exits 0, and a watchdog ends it shortly after the budget
  whatever it is doing.
- Unknown events, unknown harnesses and unparseable input answer "continue".

Turn the hooks off with `HEV_HOOKS=off` in the environment, or in
`~/.hev/config.toml`:

```toml
[hooks]
enabled = false        # default true
timeout = "2s"         # handler budget per event
halt_timeout = "10m"   # how long a halted run has to end its turn
```

## The event log

`~/.hev/hooks/events.jsonl` has one line per harness event (meta-harness
events join it in 0.7): the normalized event
without prompt text, tool input, command or tool output (their sizes only),
plus the decision, injected bytes and elapsed milliseconds. It rotates to
`events.jsonl.1` past 32 MiB. Steering latency and blocks can be read from it.

## Notifications

A notification is a handler attached to a hook event. kit has no separate
notification system: the meta-harness events `needs-you`, `ready` and `done`
run the same `hev-hook-NAME` handlers as every other event, and three kinds of
handler turn them into messages:

- **Slack**, built in. A node with [`[notify.slack]`](#slack) posts the events
  you choose to a channel or DM.
- **Your own scripts.** A `hev-hook-NAME` that rings a bell, opens a page or
  writes a file. See [hook handler delivery](#hook-handler-delivery).
- **Webhooks.** A `hev-hook-NAME` that posts the event JSON to a URL. See
  [webhooks](#webhooks).

Each of these events carries a typed **attention notice**, raised once for
each moment a person may care about, on the node where it happens. The
dispatch `notify` command and pulled member notices keep working alongside
it. As the 0.7 meta-harness events land, the same handlers can notify on them
too.

| Event | Raised when |
| --- | --- |
| `needs-you` | A run ends `needs-decision KEY: QUESTION` (an open decision), a steering halt escalates to a hard stop, or an orchestrator's round asks `[needs you] needs-decision KEY: QUESTION`. |
| `ready` | Validation passes on a run whose PR is ready with all checks green, or an orchestrator meets its goal. |
| `done` | A run ends `done`, `failed`, `timeout`, `blocked` or `needs-review`, a queued run fails admission, a repeating run ends, or an orchestrator stops or stalls. |

Only `needs-you` means a person has to act. Every other end is a record on the
opt-in `done` kind, and its `state` says which end it was. A stop someone
asked for, a halt that ended its turn in time and validator runs raise
nothing.

A `needs-you` notice is identified by its **subject**: the run or
orchestrator, the decision key and the question. Raising it again with the
same subject, as a rework or a later round that asks the same question would,
does nothing: no new notice, no hook run and no Slack post. A changed key or
question raises again.

### The notice

Each notice is JSON (`hev.attention.event/v1`):

```json
{
  "schema": "hev.attention.event/v1",
  "id": "att_5f0c9e1b2a7d4c3e8f6a1b2c",
  "time": "2026-11-17T03:12:09Z",
  "event": "needs-you",
  "source": "run",
  "name": "fix-ci",
  "host": "buildbox",
  "state": "needs-review",
  "text": "needs-decision db: Postgres or SQLite?",
  "links": {"pr": "https://github.com/example-org/project/pull/42", "run": "hev dispatch show fix-ci --host buildbox"},
  "thread": "run:buildbox/fix-ci",
  "requested_by": {"person": "user_123", "name": "Alex"},
  "addressee": ["user_123"]
}
```

`requested_by` is who asked for the work and `addressee` who the notice asks;
neither changes where it is delivered. Every host keeps an outbox of notices
at `~/.hev/attention/outbox/`, one record per notice ID.

### Hook handler delivery

Notices go to the same `hev-hook-NAME` handlers as harness events, with the
same discovery, budget, kill switch and fail-open rules. A handler gets the
kind (`needs-you`, `ready` or `done`) as its argument and in `HEV_HOOK_EVENT`,
`HEV_HOOK_HARNESS=kit`, and the notice JSON on stdin. Its output is ignored.
It runs at most once per notice ID, on the host that raises the notice.

<CodeTabs>

```sh
#!/bin/sh
# hev-hook-desk-bell: ring on anything that needs me
[ "$1" = needs-you ] && printf '\a' > /dev/tty
```

### Webhooks

A webhook is a handler that forwards the event. This one posts every
`needs-you` and `ready` notice to a URL you keep in the environment:

<CodeTabs>

```sh
#!/bin/sh
# hev-hook-webhook: forward attention notices to a URL
case "$1" in needs-you|ready) ;; *) exit 0 ;; esac
[ -n "$HEV_WEBHOOK_URL" ] || exit 0
curl -fsS -m 1 -H 'Content-Type: application/json' --data-binary @- "$HEV_WEBHOOK_URL" >/dev/null
```

<AgentPrompt>

```text
Write a kit hook handler named hev-hook-webhook in a directory on my PATH that forwards kit attention notices to a webhook. It exits quietly unless its first argument is needs-you or ready, and unless HEV_WEBHOOK_URL is set; otherwise it POSTs its stdin (the notice JSON) to that URL with curl, a 1 second timeout and Content-Type: application/json, printing nothing. Make it executable, ask me for the URL and where to set HEV_WEBHOOK_URL, and test it by piping a sample notice into `hev-hook-webhook needs-you`.
Docs: https://hevkit.com/docs/hooks#webhooks (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

Keep the request well under the `[hooks] timeout` budget (2 seconds by
default); a handler that misses it is killed and logged.

### Slack

<CodeTabs>

```toml
# ~/.hev/config.toml
[notify.slack]
channel = "U0123456789"             # a user ID opens the bot's DM; or #channel / C...
token = "secret://SLACK_BOT_TOKEN"  # a reference, read through hev secrets
kinds = ["needs-you"]               # default; add "ready", "done" to widen
# tag = "[test]"                    # optional prefix on every message
```

<AgentPrompt>

```text
Make this host post kit attention notices to Slack. Add a [notify.slack] table to ~/.hev/config.toml with channel set to the Slack user ID or channel I give you, token = "secret://SLACK_BOT_TOKEN" (or the op:// or azkv:// reference I give you; never a literal token), and kinds = ["needs-you"] unless I ask for "ready" or "done" too. Keep the rest of the file. Then run `hev s` and confirm the notify line shows no error.
Docs: https://hevkit.com/docs/hooks#slack (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

- `token` must be a reference, `secret://NAME`, `op://…` or `azkv://…`, read
  at post time through [hev secrets](/docs/secrets). The value is never
  written anywhere.
- Pass a **user ID** as `channel` to reach a person; the bot opens its own DM.
- `kinds` defaults to `["needs-you"]`. `done` always reaches hook handlers but
  reaches Slack only when listed.
- The first line of a post is `[needs you] NAME on HOST: TEXT`, then one line
  per link. Posts are threaded per run (with its steers) and per orchestrator.
- Each notice is posted at most once. A post that fails before it is sent, or
  that Slack rejects, retries with backoff. A post whose outcome is unknown is
  marked `uncertain` and never reposted; check the channel.
- A failed post never fails a run. It shows in `hev s`, the ERROR column of
  `hev dispatch ls`, and `hev dispatch show NAME`.

<Callout label="Hosts that can't post">
A host posts its own notices whenever it has `[notify.slack]`. A host without
it holds its notices for the owner to pull. `hev dispatch notices pull
--deliver` and `hev orchestrate notices pull --host H --deliver` re-emit them
on a host that has Slack config, and the stable notice ID keeps a redelivered
notice from posting twice.
</Callout>
