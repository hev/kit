A session is one coding-agent conversation: your prompts, the agent's replies
and the tool calls it made. Every file an agent opened, every command it ran
and every approach it abandoned is in there, and none of it is easy to find
once the terminal closes. kit keeps it. The `hev traces` commands list, show
and search sessions.

From 0.7, work you dispatch is also grouped into
[ask-rooted traces](#ask-rooted-traces): the ask that started the work is the
root, and the orders, attempts, validation and worker sessions it caused hang
under it.

`hevd`, the kit daemon, reads the session files your harnesses already write
and indexes new and growing ones into the archive. Files only, the archive is
a directory on each machine and search matches words. With hev layer, it is
one archive every machine shares and search is hybrid, matching meaning and
words. [Files only, or with hev layer](/docs/files-and-layer) explains the
difference. You can search from the terminal, a local web UI, a terminal
browser, or by asking Claude Code or Codex, which get a skill that searches
for them.

## What gets captured

hevd scans on an interval, every five minutes by default (`scan_interval`
under `[capture]` in `~/.hev/config.toml`). It reads these sources:

| Harness | Source | `--harness` value |
| --- | --- | --- |
| Claude Code | `~/.claude/projects` | `claude_code` |
| Codex | `~/.codex/sessions` | `codex` |
| pi | `~/.pi/agent/sessions` | `pi` |
| OpenCode | `~/.local/share/opencode/opencode.db` | `opencode` |
| dot | `~/.dot/traces` | `dot` |

OpenCode keeps sessions in a database. hevd reads it without locking or
changing it, while OpenCode runs, and supports OpenCode 2.x and 1.x. It
captures an assistant reply once it's finished, never halfway through. If an
OpenCode update changes the database layout, `hev s` shows the error instead
of skipping it.

Sessions that run as part of a dispatched [order](/docs/orders) carry the
order's ID, so you can pull up every trace behind one piece of work with
`--order`.

## Start capturing

`hev up` sets up capture on one machine: it writes the config, installs hevd
under launchd or systemd, and installs the `hev-traces` skill for Claude Code,
Codex, pi and OpenCode, whichever you have.

```sh
hev up
```

With no key this is files only. hevd writes each session to
`~/.hev/archive/hev-traces/`, your transcripts stay on this machine, and
nothing runs in Docker. To share one archive with your team on
[hev layer](https://hevlayer.com), export a key before `hev up`:

```sh
export HEVLAYER_API_KEY=...
hev up
```

The key is saved in the config, so later runs need nothing exported. Sessions
already in the file archive stay there; see
[switching later](/docs/files-and-layer#switching-later). Bringing your own
turbopuffer account is an advanced option in `hev init`.

<Callout label="Coming in 0.7">
In 0.6.2, `hev up` with no key runs a local hev layer in Docker (Postgres and a
CPU embedding model) with the dashboard at `http://127.0.0.1:8099`, and
`--store pgvector` chooses it. 0.7 replaces that with the file archive and
starts nothing in Docker.
</Callout>

To run the daemon on its own, use `hev d` (start it, or show status if it is
already running), `hev s` (status) and `hev stop`. `hev down` unloads the
daemon. The archive is kept.

## Index by hand

hevd indexes on its own. `hev index` does the same pass on demand, which is
useful for a first backfill or to see what a pass would write.

```sh
hev index                        # text and tool calls
hev index --tier all             # also tool results
hev index --limit 20 --dry-run   # parse and chunk without writing
```

Unchanged transcripts are skipped, and chunk IDs are content addressed, so
re-running is cheap and safe. Tool results are most of the bytes and the least
of what anyone searches for, so they are opt-in with `--tier tool_result` or
`--tier all`.

## Search

```sh
hev traces search "why did the preflight fail"
```

Type what you remember. kit searches prompts, replies and tool calls across
every session and returns the chunks where the words turned up, with their
session.

Add `--also` with another phrasing of the same question. Up to eight phrasings
go in one request and are fused into one ranking. Pair a natural-language
phrasing with the literal tokens you expect, such as an error string, a flag or
a file name. Files only, every phrasing matches words (BM25), and the command
says so. With hev layer, each phrasing also gets a semantic leg that matches
meaning.

```sh
hev traces search "why did the preflight fail" --also "HEVLAYER_API_KEY 401"
hev traces search --since 7d --harness codex --json "flaky deploy"
```

| Flag | Effect |
| --- | --- |
| `--also` | Another phrasing, fused in the same request. Repeatable. |
| `--since` | Only chunks from this window, such as `2h` or `7d`. |
| `--harness` | Only one harness: `claude_code`, `codex`, `opencode`, `dot` or `pi`. |
| `--workdir` | Only one working directory. |
| `--plan` | Only one plan. |
| `--order` | Only chunks from one dispatched order. |
| `--context` | Only chunks from worker sessions given one [context](/docs/context) digest. Coming in 0.7. |
| `--top` | Number of results. Default 8. |
| `--json` | Full chunk text with session and turn IDs, for scripts and agents. |

Scoping flags combine with AND.

### Ask an agent

`hev up` installs the `hev-traces` skill, so Claude Code, Codex, pi and OpenCode can search
your traces themselves. Ask "how did we fix the preflight failure last week?"
and the agent plans a few phrasings, runs them through `hev traces search`, and
reads the sessions around the best hits.

## List and read traces

```sh
hev traces                       # sessions from the last day
hev traces list --since 5d
hev traces list 2026-10-30       # one day
hev traces list --order ORDER_ID
hev traces show 3f2a             # one trace, by session ID prefix
hev traces show --json 3f2a      # normalized turns as JSON
```

`hev browse` opens the same archive in an interactive terminal browser.

## The web UI

`hev serve` runs the dashboard. It reads the file archive, or your hev layer
archive when you have a key:

```sh
hev serve                        # http://127.0.0.1:8787
hev serve --port 9000 --namespace hev-traces
```

`hev serve` binds to `127.0.0.1` by default. `--bind` takes another address, for
example a private network address so a laptop can read a headless machine's
archive. The server has no login, so only bind it where everyone who can reach
it may read every transcript.

## Ask-rooted traces

<Callout label="Coming in 0.7">
Ask-rooted traces and the dashboard's Asks view are not in a released `hev`
yet. This section describes how they are meant to work in 0.7.
</Callout>

Work rarely ends with one order. You ask for something, an order goes out, it
needs a rework, a second order follows, a validator checks the result. Each of
those leaves its own run and its own sessions. An ask-rooted trace keeps them
together: **the ask that started the work is the root of a trace**, and
everything it caused hangs under it.

### What a trace holds

| Part | What it is |
| --- | --- |
| Ask | Something a person or an agent asked for. The first ask is the root. Later asks in the same trace are follow-ups: a rework note, an amendment, a `say`, a validation request, or another order sent to continue the work. |
| Order | One order the ask sent, under its run name. |
| Attempt | One launch of that order. A rework or retry adds an attempt. |
| Validation | A browser validation run, with its verdict. |
| Session | The worker's harness session for an attempt, with its turns and tool calls. |

`hev dispatch` records the trace in the run's `meta.json`: a trace ID, the
root ask with its text, and what it can learn about who asked: the calling
tmux session, the harness and its session ID, the host and the time. The
worker starts with `TRACEPARENT` and `HEV_TRACE_ID` in its environment, so
anything it dispatches joins the same trace. When hevd indexes the worker's
session, the session row gets the trace ID too.

### New work or continued work

kit decides whether an ask starts a trace or continues one by how the work was
sent. It never guesses from an order's name.

| How the work was sent | Trace |
| --- | --- |
| `hev dispatch ORDER.md` or `hev dispatch run` | A new trace, with this order's ask as its root. |
| The same, with `--trace ID`, or `trace: ID` in the order | Continues trace `ID` with a follow-up ask. |
| `hev dispatch rework`, `retry`, `say`, `amend` or `validate` on a run | Continues that run's trace. The note, or the amendment, is the follow-up ask's text. |
| `hev dispatch` from inside a traced worker | Continues the worker's trace, under the attempt that sent it. |
| An orchestrator round with no trace to inherit, or an orchestrator's source event | Untraced, with the reason recorded. |

To send a second order as part of the same work, pass the first run's trace
ID. `hev dispatch show NAME` prints it as `trace_id`:

```sh
hev dispatch show docs-nav-refresh        # note the trace_id
hev dispatch docs-search-index.md --trace 4bf92f3577b34da6a3ce929d0e0e4736
```

`--trace` also takes a W3C `traceparent`, to say which span the new ask
follows. The sender removes a `trace:` key from the order before sending it,
so the host never sees it.

### Read the waterfall

The dashboard's **Asks** view lists traces, newest first: the root ask's text
and when it was asked, the hosts, orders, asks and runs under it, its state,
cost and duration. Open one to see its waterfall.

The waterfall reads top to bottom in the order things happened, grouped by
ask. Each ask is a row, and under it are the orders and attempts it launched,
with a bar for when each ran:

- **The root ask** comes first, then the order it sent and that order's first
  attempt and session.
- **A follow-up ask** is labelled with what it was: `continue`, `rework`,
  `retry`, `say`, `amend` or `validate`. Under it are the attempts it
  launched. When it relaunched an order that started under an earlier ask, the
  order appears as "↳ NAME · continues order" before the new attempt.
- **A validation run** sits under the ask that requested it, or under the
  attempt it checked, with its verdict.
- **A session** row opens to its turns and tool calls. "open ↗" opens the
  session in the transcript view, with a breadcrumb back to the trace, the ask
  and the order.

Choose an order to see only its asks and runs within the trace. Each order
chip on the trace page does the same.

### Untraced runs

A run with no trace context is listed in the Asks view as **untraced**, never
hidden. That covers runs dispatched before 0.7, orchestrator launches that had
no trace to inherit, and runs whose `meta.json` was rewritten by an older
`hev`. An untraced run stays untraced through its reworks and retries: kit
does not invent a trace for it later.

### Limits

- The Asks view reads run records from the host serving the dashboard. A trace
  whose runs are split across hosts shows the runs on that host, and lists the
  other sessions in the trace below the waterfall.
- The root ask's text is the order's body, up to `## Acceptance`. The prompt
  you typed in your own session is not linked yet.
- Runs from before 0.7 are not backfilled into traces.

## Shared archives

With a hev layer key, the archive is one namespace that every machine with the
key writes to. `hev open` opens it in the browser, and `hev join CODE` joins
one you were invited to. See
[Files only, or with hev layer](/docs/files-and-layer).

## Sensitive data

Coding-agent sessions hold whatever the agent saw: keys pasted into a prompt,
secrets on a command line, file contents, customer data. hevd indexes every
session in the sources above on each machine it runs on.

kit scrubs secrets before anything is written. Scrubbing is on unless you set
`redact = false` under `[capture]`. It uses the gitleaks rule set plus rules for
common API tokens, private keys, JWTs, credentials in URLs and high-entropy
assignments, and replaces each match with a fingerprint. It cannot catch every
password, encoded secret or split token, and the source transcripts on disk stay
raw.

Run hevd on machines whose sessions you are comfortable storing in the archive,
and treat the archive directory, the namespace, its key and any bound
`hev serve` address with the same care as the transcripts.
