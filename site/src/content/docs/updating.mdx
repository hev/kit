`hev update` moves a host's `hev` to another build published by the official
repository, [hev/kit](https://github.com/hev/kit/releases). It verifies the
build, installs it beside the one it replaces, switches over atomically and
restarts what runs from it. `hev dispatch hosts update` asks every host you
own to do the same.

## Channels

A host follows one channel, set in its own config:

| Channel | What it is |
| --- | --- |
| `release` | The latest published release. The default. Nothing changes for a host that never opts in. |
| `edge` | The newest edge build: the tip of the open release train branch `vX.Y`, built and tested on every push like a release, and published as a pre-release tagged `edge-X.Y.Z-edge.<sha>`. Versions read `X.Y.Z-edge.<sha>`. |

Edge is for an operator who wants their own hosts to run each merged feature
before it is released. Users install releases.

## `hev update`

| Command | What it does |
| --- | --- |
| `hev update` | Move to the newest build on this host's channel. |
| `hev update --channel edge` | Record `edge` as this host's channel and move to the newest edge build. `--channel release` records `release`; the host moves once a release is newer than what it runs, or now with `--to`. |
| `hev update --to VERSION` | Move to a named build: `X.Y.Z` or `X.Y.Z-edge.<sha>`. This may move backwards; the channel alone never does. |
| `hev update --check` | Report the newest build on the channel and whether this host is behind. Changes nothing. |
| `hev update --rollback` | Return to the build the last update replaced. Running it again goes forward again. |

`--json` prints the report. A host already on the newest build reports so
and changes nothing.

### What an update does

1. Reads the build's `manifest.json` (a release published before manifests:
   its `checksums.txt`), checks it names the version asked for, and
   downloads the archive for this OS and architecture.
2. Checks the archive's sha256 against the manifest. A mismatch stops the
   update. Nothing has been replaced.
3. Unpacks `hev` into `~/.hev/versions/VERSION/` and runs it once
   (`hev version`) to check that it starts.
4. Keeps the build being replaced under `~/.hev/versions/` too, then switches
   the `hev` you ran (and `~/.local/bin/hev`, which `hev up` installs for the
   daemon, if present) to the new build atomically. On macOS and Linux that
   path becomes a symbolic link to the versioned file, swapped in with one
   rename. On Windows, see [below](#windows).
5. Restarts the capture daemon through its service manager and waits for it
   to stay up. If it does not, the update switches back to the previous
   build, restarts it again, and says so.
6. Refreshes bundled skills from the new binary (`hev skills sync`), where a
   Claude Code, Codex or shared agents skills directory exists.
7. Runs the host's own `post_update` commands, if any.

Runs in progress are never signalled. Each keeps the binary it started with
to the end, and new runs start on the new build. The current build, the
previous one and the three most recent others stay under `~/.hev/versions/`,
so a long run's binary is still there when it next executes itself.

### What restarts

| Platform | Restarted | How |
| --- | --- | --- |
| macOS | `hevd`, the LaunchAgent `com.hev.hevd`, if `hev up` installed it | `launchctl kickstart -k`, then checks it keeps one running process |
| macOS | the secrets cache, the LaunchAgent `com.hev.secrets`, if installed and loaded | as for `hevd` |
| Linux | `hevd`, the systemd user unit `hevd.service`, if `hev up` installed it | `systemctl --user restart`, then checks it stays active |
| Linux | the secrets cache, the systemd user unit `hev-secrets.service`, if installed and active | as for `hevd` |
| Windows | `hevd`, the scheduled task `hev\hevd`, if installed | ends and runs the task, then waits for the daemon to report |

A daemon you started by hand (`hev d`) is named in the report, not killed;
restart it yourself. Dispatched runs and their supervisors are not
restarted. The dashboard container is not restarted; run `hev up` for it.

The secrets cache runs inside `hevd`, or, on a host without `hevd`, as
`hev daemon --secrets-only` under the job from
[Secrets](/docs/secrets#switch-the-cache-on). Restarting it sends no request:
it fills again on demand, and a rate-limit cooldown on disk still holds.

### Package managers

`hev update` never replaces a file a package manager owns. On a Homebrew
install it stops and says what to do instead: `brew upgrade hev/tap/hev`
for releases. Homebrew installs releases only. To follow edge on such a
machine, `brew uninstall hev`, install from a release archive into a
directory you own that is on your PATH (`~/.local/bin`, where `hev up`
already puts the daemon's copy), and run `hev update --channel edge` from
there. Nix, Scoop and system package directories (`/usr/bin`) are treated
the same way.

### Windows

A running `hev.exe` cannot be overwritten. `hev update` renames it aside
(`hev.exe.old-…`), moves the new build into its name, and removes the old
file on a later update, once nothing runs it. The scheduled task is ended and run again. A
daemon that updates itself exits and the task restarts it within a minute.

## The `[update]` table

In the host's own config (`~/.hev/config.toml`, or `$HEV_CONFIG`):

<CodeTabs>

```toml
[update]
channel = "edge"        # release (default) or edge
auto = false            # let the daemon update this host on a schedule
interval = "1h"         # how often the daemon checks; at least 1m
post_update = [         # run after each successful update or rollback
  "systemctl --user restart my-wrapper.service",
]
```

`post_update` is for an operator's own services that wrap `hev`. Each
command runs through the shell with `HEV_UPDATE_FROM`, `HEV_UPDATE_TO` and
`HEV_UPDATE_CHANNEL` set. A failing hook is reported; it does not undo the
update. Hooks come only from this file: never from a sender or the network.

`hev update --channel` edits only the `channel` line, so comments and other
settings stay as they are.

## Automatic updates

With `auto = true` and a `channel` set, the capture daemon checks on its
`interval` and updates the host by the same path as `hev update`. Both are
needed; automatic updates are off by default.

- It checks only between its own scan cycles, never in the middle of one.
- After switching it re-executes itself from the same path, now the new
  build, and the new daemon confirms the update after a clean cycle. If the
  new build fails to start three times, the next start switches back.
- A failed check backs off: the interval doubles with each failure, up to a
  day, and resets on success.
- It never moves a host backwards.
- Everything it does is recorded in `~/.hev/update/state.json` (history,
  last and next check, failures) and in `~/.hev/hev.log`.

## Updating every host

From the machine you dispatch from:

<CodeTabs>

```sh
hev dispatch hosts                                   # VERSION, CHANNEL and BEHIND per host
hev dispatch hosts update --all --check              # what would change
hev dispatch hosts update --all                      # each host to the newest build on its channel
hev dispatch hosts update --host HOST --channel edge # one host, moved to edge
hev dispatch hosts update --all --to X.Y.Z           # every host to a named build
```

<AgentPrompt>

```text
Update the hosts I own from this machine. Run `hev dispatch hosts` and report each host's VERSION, CHANNEL and BEHIND, then `hev dispatch hosts update --all --check` and show me what would change. After I confirm, run `hev dispatch hosts update --all`, or `--host HOST --channel edge` for one host, or `--all --to X.Y.Z` for a named build, as I ask. Report each host's version before and after, or why it did not update. Finish with `hev dispatch hosts` to show none is behind.
Docs: https://hevkit.com/docs/updating#updating-every-host (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

Each host runs the update on itself and the command prints, per host, the
version before and after, or why not. `hev dispatch hosts` shows each host's
channel and whether it is behind it (for edge, by how many commits).

- **Owner only.** A host accepts the request only from its owner. An
  invited member's request is refused by the host.
- **The request carries a channel and a version, nothing else.** The host
  fetches the build from the official repository and verifies it itself. A
  sender cannot supply a binary, a URL, a digest or a command.
- **Older hosts.** A host on a release from before this command answers with
  an error that says so; move it by hand once
  ([below](#moving-a-cluster-to-edge-the-first-time)). Hosts update at
  different moments, so each build talks to the build before it, both ways.

## Trust model

What `hev update` fetches, and from where, is fixed in the binary: the
releases of `github.com/hev/kit`, over HTTPS (`api.github.com` to find the
newest build, GitHub release downloads for the files). No flag, config key
or request field changes it.

| Who | Can | Cannot |
| --- | --- | --- |
| Someone on the network | Block or slow the download: the update fails and nothing changes. | Substitute a file or an older listing: TLS with the system's certificate authorities stops that, and a corrupted or truncated download fails the digest check. |
| A sender with dispatch access | An owner can move a host to any published build, including an older one with `--to`. An invited member can do nothing: the host refuses. | Supply a binary, a URL, a digest or a hook. Name anything but a published `hev/kit` version. |
| Whoever controls the repository's releases | Publish a build that every host following that channel will install. | Nothing more is needed: this is the same trust as installing a release. |

The manifest and the archive come from the same release, so the digest
proves the release is consistent and the download intact. It does not prove
who built it. Edge builds come only from pushes to a train branch, which
are reviewed pull requests, and every archive carries a signed GitHub build
provenance attestation naming the workflow and commit that built it. Check
one by hand with:

<CodeTabs>

```sh
gh attestation verify kit_X.Y.Z-edge.SHA_linux_amd64.tar.gz --repo hev/kit
```

<AgentPrompt>

```text
Check the build provenance of a kit release archive: run `gh attestation verify kit_X.Y.Z-edge.SHA_linux_amd64.tar.gz --repo hev/kit`, with the archive file I downloaded. It needs the GitHub CLI, logged in. Tell me whether it verified and which workflow and commit the attestation names.
Docs: https://hevkit.com/docs/updating#trust-model (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

`hev update` does not verify attestations itself: that needs a Sigstore
verifier and its trust root inside the binary, a large dependency for a
check that would not stop a malicious change merged through review.

## Moving a cluster to edge the first time

Hosts on 0.6.2 or earlier have no `hev update` and do not know the request,
so each moves by hand once. After that, one command moves them all.

On each host, including the one you dispatch from:

1. Find the newest edge build on the
   [releases page](https://github.com/hev/kit/releases) (pre-releases tagged
   `edge-X.Y.Z-edge.SHA`). Download the archive for the host's OS and
   architecture and `checksums.txt`, and check it:

   <CodeTabs>

   ```sh
   V=X.Y.Z-edge.SHA; OS=linux; ARCH=amd64         # or darwin, arm64
   curl -fLO "https://github.com/hev/kit/releases/download/edge-$V/kit_${V}_${OS}_${ARCH}.tar.gz"
   curl -fLO "https://github.com/hev/kit/releases/download/edge-$V/checksums.txt"
   sha256sum --check --ignore-missing checksums.txt   # macOS: shasum -a 256 --check --ignore-missing
   tar -xzf "kit_${V}_${OS}_${ARCH}.tar.gz" hev
   ```

   <AgentPrompt>

   ```text
   Download and check an edge build of hev on this host. Find the newest pre-release tagged edge-X.Y.Z-edge.SHA on https://github.com/hev/kit/releases and set V to its version, OS to linux or darwin and ARCH to amd64 or arm64 for this machine. Download kit_${V}_${OS}_${ARCH}.tar.gz and checksums.txt from that release with curl, run `sha256sum --check --ignore-missing checksums.txt` (on macOS `shasum -a 256 --check --ignore-missing checksums.txt`) and stop if it fails. Extract only hev with `tar -xzf "kit_${V}_${OS}_${ARCH}.tar.gz" hev`, then run `./hev version` and show me the version.
   Docs: https://hevkit.com/docs/updating#moving-a-cluster-to-edge-the-first-time (all pages: https://hevkit.com/llms.txt)
   ```

   </AgentPrompt>

   </CodeTabs>

2. Put it where the host runs `hev` from: the `hev` on the PATH that SSH
   sees, and `~/.local/bin/hev` if `hev up` installed the daemon there.
   `install` replaces the file without disturbing a running one:

   <CodeTabs>

   ```sh
   install -m 0755 hev "$(command -v hev)"
   [ -e ~/.local/bin/hev ] && install -m 0755 hev ~/.local/bin/hev
   ```

   <AgentPrompt>

   ```text
   Install the hev binary I just downloaded and checked in this directory over the one this host runs: run `install -m 0755 hev "$(command -v hev)"`, and if ~/.local/bin/hev exists, `install -m 0755 hev ~/.local/bin/hev` too. If `command -v hev` points into Homebrew, a system directory or another package manager's path, stop and tell me. Verify with `hev version` that the new build runs.
   Docs: https://hevkit.com/docs/updating#moving-a-cluster-to-edge-the-first-time (all pages: https://hevkit.com/llms.txt)
   ```

   </AgentPrompt>

   </CodeTabs>

   A Homebrew host: see [Package managers](#package-managers). On Windows,
   end the task (`schtasks /End /TN hev\hevd`), extract `hev.exe` over the
   old one, and run it again (`schtasks /Run /TN hev\hevd`).

3. Restart the daemon, refresh skills and record the channel:

   <CodeTabs>

   ```sh
   launchctl kickstart -k gui/$(id -u)/com.hev.hevd   # macOS
   systemctl --user restart hevd.service              # Linux
   hev skills sync
   hev update --channel edge                          # records the channel; reports it is current
   ```

   <AgentPrompt>

   ```text
   Finish moving this host to the edge channel: restart the capture daemon with `launchctl kickstart -k gui/$(id -u)/com.hev.hevd` on macOS or `systemctl --user restart hevd.service` on Linux, refresh skills with `hev skills sync`, then run `hev update --channel edge` to record the channel. Show me that it reports this host current, and check with `hev s` that the daemon is running.
   Docs: https://hevkit.com/docs/updating#moving-a-cluster-to-edge-the-first-time (all pages: https://hevkit.com/llms.txt)
   ```

   </AgentPrompt>

   </CodeTabs>

Then, from the machine you dispatch from, check that every host answers:

<CodeTabs>

```sh
hev dispatch hosts
hev dispatch hosts update --all --check
```

<AgentPrompt>

```text
After moving my hosts to edge by hand, check them from the machine I dispatch from: run `hev dispatch hosts` and `hev dispatch hosts update --all --check`. Report each host's version, channel and whether it is behind, and name any host that does not answer or reports an error.
Docs: https://hevkit.com/docs/updating#moving-a-cluster-to-edge-the-first-time (all pages: https://hevkit.com/llms.txt)
```

</AgentPrompt>

</CodeTabs>

**Keeping it there.** Either let each host follow edge itself, by adding
`auto = true` under `[update]` in its config, or move them all after merges
with `hev dispatch hosts update --all`. `hev dispatch hosts` shows any host
behind. To leave edge, `hev dispatch hosts update --all --channel release`
moves each host to the latest release once it is newer than what it runs,
or `--to X.Y.Z` moves them now.
