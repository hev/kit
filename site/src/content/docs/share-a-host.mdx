The most out of this setup comes from sharing one host across a team of
developers. The host carries the repos, the bot's identity and credentials,
the installed tools and skills, and the trace archive. Each developer sends it
work from their own laptop, and nothing on the laptops is shared with it.

A host can be a physical machine, a VM, or both: a team might share a Mac mini
for app and browser work and a Linux VM for builds. Each is its own host with
its own owner, members and admission list.

The host account is set up like a new hire: its own bot identity, accounts and
keys, given only the repositories and services it needs, with a human
approving its work. **The sandbox is the computer:** use a dedicated machine
for risky autonomy.

## Roles

| | Owner | Member |
| --- | --- | --- |
| Access | Shell on the host, usually root or admin | An SSH key locked to `hev dispatch rpc`, no shell |
| Gets it by | Running the machine | `hev nodes join`, accepted by the owner |
| Send runs | Yes | Yes |
| List, show, logs, say, stop | Every run | Their own runs |
| Hear when a run finishes | Pushed to their session | `hev dispatch notices pull` |
| Attach, clean, amend, rework, validation, orchestrators | Yes | No |
| Install software, set credentials | Yes | No |
| Set the admission list and `add_from` | Yes | No |
| Add and remove repos | Yes | Only with the `repos` permission, within `add_from` |
| Invite and remove members, grant permissions | Yes | No |

**Owner.** Whoever controls the host: root or an administrator, or the bot
account itself. The owner installs hev, the agent harnesses and the bot's
credentials, writes `~/.config/hev/dispatch.toml`, and manages members. Anyone
given an ordinary SSH key or a login to the host account is an owner in
practice, because they can edit every file that account can, its admission
policy and credentials included.

**Member.** A developer who joined with an invite code. Their key runs one
command, `hev dispatch rpc`, which allows sending runs and managing their own.
Every run is stamped with the member's name (`requested_by`), so reports, pull
requests and traces show who asked for the work. A member can't change their
name in a request.

**Permissions.** The owner can give a member extra rights one at a time.
Today there is one: `repos`, which lets a member add and remove repos from the
organizations the owner allows. See
[Admission](/docs/admission#let-members-add-repos).

<Callout label="A member's agents act as the host account">
The member boundary limits what a member can ask hev to do. It doesn't limit
what an agent does once it runs. Agents run as the host account, with its
files, credentials and network, so a member can write an order that asks an
agent to read the bot's credentials or change the host's files. Invite only
people you'd trust with that account. Keep the account itself narrow: scoped
bot credentials, no admin rights where you can avoid them, and nothing on the
machine the team shouldn't reach. Tighter member controls are planned.
</Callout>

## Set up the host

Complete [headless setup](/docs/hosts#add-a-headless-machine) first: install
hev, Git, tmux and an authenticated agent harness; clone the repos under
`~/workspace`; set up the bot's Git and PR credentials. Keep `hev` and the
harness on the PATH seen by noninteractive SSH, at a stable absolute path,
since members' keys refer to it directly.

Put the host on a private network your members can reach, such as Tailscale
or your VPN, and allow its SSH port. hev doesn't provision the network or OS
accounts. No public SSH or dashboard port is needed.

## Invite a member

On the host, make a one-use invite code:

```sh
hev nodes invite alex --address build.example.test --user bot --expires 1h
```

The code holds the address, the pinned host key and its fingerprint, the
expiry and a random token. Send it privately. The member runs
`hev nodes join CODE`, which creates a dedicated key and SSH alias on their
laptop and prints a request. Check the request came from them, then accept it:

```sh
hev nodes accept REQUEST
hev nodes accept REQUEST --allow repos   # also let them add and remove repos
hev nodes ls
```

On Windows, run as the SSH account. If that account is an administrator, use
`hev nodes accept REQUEST --administrators`, which writes
`C:\ProgramData\ssh\administrators_authorized_keys`. See
[Windows](/docs/windows).

Change permissions later without a new invite:

```sh
hev nodes allow alex repos
hev nodes deny alex repos
```

## Remove a member

```sh
hev nodes remove alex
```

This revokes the grant and removes exactly that member's key line. It doesn't
stop runs already going; stop those with `hev dispatch stop`. Remove their
network access too.

## Admit repos

The host runs work only against repos on its admission list:

```toml
workspace = "~/workspace"
cap = 4

[admission]
repos = ["https://github.com/example-org/my-project.git"]
add_from = ["https://github.com/example-org/"]
```

`repos` is the list; `add_from` is where members with the `repos` permission
may add from. See [Admission](/docs/admission) for matching rules and member
adds. Admission covers repos only.

## Set up skills

On the host, install hev's skills for the host side:

```sh
hev skills setup --role host
```

To give the host and members' laptops your team's own skills, put them in a
skills repo and add it to `~/.hev/config.toml` on each machine:

```toml
[[skills.sources]]
url = "https://github.com/example-org/skills.git"
ref = "refs/heads/main"
subdir = "skills"
```

`hev skills setup` installs it, pinned to a commit, alongside hev's own
skills. Members run `hev skills setup` after you accept them; on a laptop
whose only hosts are ones it joined, it installs `hev-member` instead of the
owner-only `hev-dispatch` and `hev-expedite`. Run setup with `--role host` on
the host the first time; it won't guess. Install MCP configuration and secrets on the host
yourself.

## Share traces

Runs on the host are captured to its archive. To let members read it without
SSH access, serve the dashboard on the private network only:

```sh
hev serve --bind 100.64.0.10 --port 8788
```

Members open `http://100.64.0.10:8788`. Anyone who can reach that address can
read everything the archive holds, so bind it to the private network, never a
public interface.

To add members' laptop sessions to the same archive, give the team one API
key scoped to the team's namespace, delivered through your password manager.
Each member sets `HEVLAYER_API_KEY` and `HEVLAYER_NAMESPACE` and runs
`hev up`. See [Traces](/docs/traces).
