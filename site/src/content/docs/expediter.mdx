Dispatching an order is the easy part. Someone still has to read the report,
notice the test that was skipped, send rework, ask for validation and tell you
when the PR is ready. That someone can be you. It can also be an agent. In a
kitchen that job is the expediter, and the name stuck.

Expediting is optional. `hev expedite` starts a repeating agent order to
follow runs for your current peer session. You can still follow them yourself.

## What it does

For each run it's watching, an expediter:

- reads `hev dispatch show NAME` when the run ends, and checks `report.md` and
  the PR against the order's Acceptance items;
- sends `hev dispatch amend NAME revised.md` when an item isn't met, with
  the corrected order and Acceptance items;
- runs `hev dispatch validate NAME` or `rework --from-validation` for browser
  orders;
- stops at `needs-review` and hands the run to a person;
- tells you when a run is ready for you, and only then.

The default `review` authority permits review and rework, and never merges.
`merge-on-green` also permits merging reviewed and independently verified PR
heads with green CI. Neither permits deployment, tags, releases or live
configuration changes.

## Peers, both ways

An expediter only works if it hears about runs and can be asked about them.

- **Inbound from runs.** Point the order's `reply` at the expediter's
  [peer](/docs/peers) session name, and make the target host's `notify` command
  deliver to it. The expediter gets a message when each run ends and when a
  validation verdict comes back.
- **Inbound from people and agents.** Anyone can ask it "where is X?" through
  `hev peers send`. It should answer.
- **Outbound.** It reports to you, and to whoever dispatched the order, the
  same way.

If it only polls `ls` and never answers, it's a cron job with opinions.

## Is it worth it?

It's good practice once you have more runs in flight than you can comfortably
check. It's up to you. For a handful of orders, following them yourself, or
asking the agent that dispatched them to keep an eye out, often works best. An
expediter adds a second reader with its own blind spots; it is not a
substitute for reading the PR.

## Start and stop

```sh
hev expedite --host buildbox --authority review --every 10m --max-lifetime 24h
hev expedite status
hev expedite stop
```

Run it from your front-of-house terminal. It resolves your current peer
address and snapshots runs whose `reply` exactly matches that address.
All inventory hosts must be reachable. New runs are not enrolled automatically.
Set `--host`, or configure `default_host`. The host must support headless
dispatch. The worktree uses the first followed run's repo; `--repo` overrides
it. Only one active expediter per reply session is allowed.

The bundled, versioned `hev-expedite` skill directs each round to read its
inbox and chats, review completed work and independently verify it. Missing
tools or an unavailable verification model are reported as `[needs you]`.
Findings use `hev dispatch amend` and retain the run's branch and PR.

The skill records evidence by head SHA and calls `hev expedite round`.
The helper rechecks run state and GitHub checks. Empty, pending, skipped,
neutral or failed check sets block readiness. Changed heads need new review;
merge uses GitHub's matching-head condition. Evidence is an agent attestation.

It stops when all followed runs are merged or explicitly abandoned, when
you run `stop`, or at maximum lifetime. A closed unmerged PR needs explicit
abandonment from a person. **Run `hev expedite stop` when reopening your
session.** There is no automatic wake detector. Use `--host HOST` and a name
to inspect or stop from another session.

When the owner has `[board].url` or `FACTORY_BOARD_URL`, the supervisor posts
a final handoff. A failed handoff leaves `handoff.md` and `handoff-error` in
the run directory. `hev dispatch show NAME` keeps the detailed round record.
